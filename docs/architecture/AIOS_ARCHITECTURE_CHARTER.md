# AIOS Architecture Charter

## 1. Purpose
AIOS (Advanced Agentic Operating System) は、政治・現場統制の意志決定およびオペレーションをリアルタイムに統合管理する「FIELD OPERATIONS OS」の基盤です。  
本アーキテクチャ憲章（Architecture Charter）は、AIOSにおけるすべてのサブシステム（Dashboard OS / Runtime OS / Kernel OS / Development OS）の設計・開発・拡張において遵守すべき**最高設計原則（Single Source of Truth）**を定義します。  
本憲章は、一時的な実装要件や個別AIモデルの選定よりも高い優先度を持ち、すべての開発プロセス、コミット、および Quality Gate の監査基準となります。

---

## 2. Core Design Principles (核心設計原則)

AIOSにおけるすべての機能ブロックは、以下の設計規格を厳格に遵守しなければなりません。

* **Foundation First (基盤優先原則)**
  * すべてのシステム開発は、まず不変（Immutable）かつ決定論的（Deterministic）な基盤（Foundation）から構築します。機能追加や最適化は、基盤が安定・検証された後にのみ許容されます。
* **Deterministic (決定論的動作の保証)**
  * システムの挙動は、入力データと初期状態が同一であれば、実行環境（ブラウザ、サーバー、時間、乱数）に関わらず完全に同一でなければなりません。
  * `Math.random()` や `Date.now()` を用いた非決定的なID・タイムスタンプ・配置の決定は、Foundation および State 制御において一切禁止します。一意なID生成には単調増加カウンタ等の決定論的手法を用います。
* **Immutable (状態の不変性)**
  * レジストリ（Registry）、メタデータ、コンテキスト（Context）、および状態ストア（State Store）のオブジェクトは、生成または初期化された後、一切の変更を禁止します（`Object.freeze` 等による凍結）。
  * 状態の遷移は、古い不変オブジェクトから新しい不変オブジェクトへの完全な置換（Re-create）としてのみ行われます。
* **Single Responsibility (単一責務の原則)**
  * 1つのモジュール、クラス、コンポーネントは、1つの独立した責務のみを持ちます。
* **Stateless (ステートレス設計)**
  * 中継ロジックや描画ロジックは、極力内部状態を持たず、与えられた入力（PropsやState Store of コピー）のみに基づいて振る舞いを決定します。
* **Registry Pattern**
  * 静的な定義（ウィジェット、レイアウト、ナビゲーション等）は、すべて Registry に集約して読み取り専用で管理し、実行時に動的なインライン定義を行いません。
* **Adapter Pattern**
  * 外部API、デバイス、または他のOS層との結合はすべて Adapter を介して疎結合化し、モジュールが外部環境に直接依存することを防ぎます。
* **EventBus Pattern**
  * レンダラー、状態マネージャー、実行エンジン間の通信は、`DashboardEventBus` のような一方向の Pub/Sub イベント仲介を介して行い、直接参照を防止します。
* **Observer Boundary (観測境界)**
  * ダッシュボードやビューコンポーネントは、データを観測して表示することのみを担当する「Observer（観察者）」であり、ダッシュボード側からシステムへの書き込み（Write）、自律的な意思決定（Decision）、またはAPIコマンドの送信を行うことは禁止されます。
* **Backward Compatibility & Versioning Policy**
  * すべてのAPI契約およびJSONスキーマは、後方互換性を保証します。APIの仕様変更時は段階的なマイグレーションルールを適用し、既存のクライアント展開構造（config.js の差し替え等）を破壊してはなりません。

## 3. Architecture Layers (アーキテクチャ層)

AIOSは以下の4つの厳密な階層に分離されます。階層間の依存方向は「下位から上位への依存」を禁止する一方向ルールとします。

1. **Dashboard OS (UI / UX 観測層)**
   * **責務**: `DashboardRenderer` 及び UIカード群による決定論的描画と、`EventBus` からの更新通知の受信。
   * **制約**: Observer Boundary を厳守。データ書き込みや外部APIコール、AI判断ロジックは一切持たない。
2. **Runtime OS (初期化・ライフサイクル制御層)**
   * **責務**: 各種 Foundation レジストリ、状態ストア、レンダリングパイプラインの起動・初期化順序（Boot sequence）を一元管理する。
   * **制約**: システム稼働後は状態変化を監視し、自己修復などの自律的な操作（Write）は行わない。
3. **Kernel OS (データ中継・実行制御・セキュリティ層)**
   * **責務**: 現場データの供給、認証、ライセンス管理、認証トークン伝播、セキュリティ暗号化等のバックエンドAPI通信制御。
   * **制約**: UIのレンダリングやレイアウト処理には一切干渉しない。
4. **Development OS (自律開発・エージェント支援層)**
   * **責務**: コードの自律修正、リファクタリング、監査、品質測定などのエージェント環境支援。
   * **制約**: 稼働中の本番システム（Kernel/Runtime）に直接干渉せず、検証ゲート（Quality Gate）を介したコード変更としてのみ適用する。

## 4. Dependency Rules (依存ルール)

モジュール間の参照ルールを以下のように固定し、循環参照（Circular Dependency）や責任限界の逸脱を防ぎます。

* **Dashboard OS は Tool / Engine を知らない**
  * UIコンポーネントが、外部のデータ収集ツール、LLM、または実行エンジンを直接インポート、インスタンス化、呼び出しすることは一切禁止します。
* **Kernel OS は IDE を知らない**
  * API中継やデータ整合層が、開発環境（VSCode、Git、clasp）に依存してはなりません。
* **Development OS は IDE へ直接依存しない**
  * 開発・監査エージェントのアダプターは抽象化された API を通してアクセスし、特定のローカルエディタやシステム環境変数に直接結合してはなりません。
* **外部依存の隔離 (Adapter Rule)**
  * 外部サービス（Spreadsheet, Stripe, LINE, LLM API）へのアクセスは、すべて専用の `Adapter` クラス内部にカプセル化されなければなりません。ビジネスロジックや Foundation のコアがこれらを直接 `fetch` することは禁止されます。

---

## 5. Foundation Rules (基盤実装のルール)

すべての Foundation モジュールは以下の基準を100%満たす必要があります。

* **Pure Foundation**: 純粋なデータマッピング、バリデーション、およびライフサイクル状態管理のみを担当する。
* **No External Dependency**: ブラウザの標準組み込み API 以外の外部ライブラリ（Lodash, jQuery 等）に依存してはならない。
* **Immutable**: 初期化時に `Object.freeze` で凍結された静的データを返す。
* **Deterministic**: 乱数・日付をキーにせず、事前に定義された静的キーまたは単調増加カウンタを用いてIDを解決する。
* **One Module = One Responsibility**: 単一のソースファイルは、1つのレジストリ、1つのファクトリ、あるいは1つのアダプターのみを定義する。

## 6. Development Rules (開発プロセスルール)

Development OS 層および開発エージェントが適用するルールです。

* **Capability Driven**: すべての機能実装は、その機能が提供する「Capability（能力・権限境界）」に基づいて構成され、無制限なファイル書き換えやコマンド実行は禁止されます。
* **Registry Driven**: 実装されるコードやモジュールは、対応する Registry に静的に登録され、そこからのみ参照可能でなければなりません。
* **Adapter Driven**: 外部開発環境への統合は、抽象化された Tool Adapter を介して実行されます。
* **Quality Gate Driven**: すべてのコード変更は、本番環境への反映前に必ず「Quality Gate（テスト自動回帰と静的解析）」をパスしなければなりません。
* **Architecture Decision Records (ADR) の適用**
  * AIOSのアーキテクチャ上の重要な設計判断は、すべて `Architecture Decision Record (ADR)` として記録し、後から決定プロセスおよびトレードオフを追跡・レビュー可能にしなければなりません。
* **Extension Principle (拡張の原則)**
  * 新しい機能やモジュールを追加する際は、稼働検証済みの既存の Foundation ファイルを直接改変するのではなく、新しい `Module`、`Registry`、`Adapter` を追加して機能拡張を行います。既存 Foundation の直接変更は原則として禁止します。

---

## 7. Quality Rules (品質・レビュー基準)

すべての設計レビュー（Architecture Review）および自動テスト（Quality Gate）において、指摘事項は以下の3段階に分類されます。

* **Critical (致命的)**
  * **定義**: セキュリティ漏洩、マルチテナント境界の突破、不変オブジェクトの強制改変、非決定論的設計の混入、循環参照、または本番システム起動不可。
  * **対応**: 即時デプロイおよびマージをブロック。修正されるまで次のフェーズに進めません。
* **Major (重大)**
  * **定義**: アーキテクチャ層の直接的な依存ルール違反（DashboardがKernel APIを直叩きするなど）、モジュールの責任境界逸脱、イベントの不整合、またはテストのカバレッジ不足。
  * **対応**: リリースブロック。承認された設計修正案に基づいてコード修正が必要です。
* **Minor (軽微)**
  * **定義**: コメント・ドキュメントの不整合、型注釈の欠落、冗長なコードパス。
  * **対応**: ログ記録を行い、次のデプロイスプリントで修正。本番リリースを即時ブロックはしないが、次のマイルストーンまでに解消必須。

---

## 8. Release Rules (リリースルール)

* **Versioning**: セマンティックバージョニング（`vX.Y.Z`）を適用します。
* **Tag Rule**: リリース時は必ず Git Tag を付与し、リリース成果物のコミットハッシュを厳密に固定します。
* **Baseline Freeze**: 一度リリースされた `vX.Y.Z` バージョンの Foundation モジュールは、次のメジャー/マイナーバージョンアップ時まで一切の変更を凍結します。

---

## 9. Charter Enforcement (憲章の強制力)

本憲章に定められた原則への違反は、開発ツール（Development OS）および静的コード解析によって自動的に検出されるべきであり、如何なる理由があっても**憲章違反は `Critical Violation` として品質ゲートにより拒絶されます。**
原則の変更が必要な場合は、開発者およびステークホルダーによる明示的な同意を経て、本憲章ファイルを変更・コミットすること（ADRの追加）によってのみ認められます。
