# Project Services Foundation Specification

## Purpose

Project Services Foundation defines the abstract service framework of the AIOS Platform. It establishes a unified lifecycle and access control mechanism for all project-level platform utility services (such as Launcher, Diagnostics, Installer, and Marketplace), decoupling service orchestration from service instantiation and execution.

---

## Services Constitution

The Project Services module conforms to the following strict architectural constraints:

> ### Services Foundation Never Executes
> 
> 1. **Framework Only**: The Services Foundation is a registration and lifecycle plane; it does not launch workloads.
> 2. **No Execution/Initialization**: It must never execute commands, spawn child processes, or run shell scripts.
> 3. **Pure Locator Pattern**: The `ProjectServiceRegistry` is a pure Service Locator. It must never instantiate service objects internally (no `new` operations). Instances must be generated by a Bootstrap composition root and registered externally.

---

## Service Architecture Flow

The framework operates under a unified locator interface:

```
[Composition Root (AIOS Bootstrap)]
      │
      ├──> Generates service instances (new LauncherService, etc.)
      │
      ▼
[ProjectServiceRegistry (Locator)] <── Registers instances
      │
      ├──> register(service)
      ├──> lookup(id)
      ├──> initializeAll() ───> Sequentially initializes all services
      └──> shutdownAll() ─────> Shuts down all services in reverse order
      │
      ▼
[IProjectService (共通インターフェース)]
      ├──> [LauncherService (骨組み)] ────> Handles initialization/lifecycle (No launch() API)
      └──> [DiagnosticsService (骨組み)] ──> Handles initialization/lifecycle (diagnose() throws Error)
```

---

## Service State Lifecycle Machine

Every service implementing `IProjectService` transitions through a strict, sequential state machine:

```
[Created] ──(initialize())──> [Initialized] ──(shutdown())──> [Stopped]
```

* **`Created`**: Default state upon instantiation by the composition root.
* **`Initialized`**: State after the service has loaded internal dependencies and variables.
* **`Stopped`**: State after the service has cleaned up resources.
* *Note on `Running` state*: The `Running` state is defined for future active loops but is unused in G6-10.

---

## Skeleton Constraints

To maintain a strict separation of concerns, concrete services are limited to skeleton implementations:

1. **`LauncherService`**:
   - Implements `IProjectService` lifecycle.
   - Does **not** expose a `launch()` method. The launch APIs are deferred to Sprint G6-11.
2. **`DiagnosticsService`**:
   - Implements `IProjectService` lifecycle.
   - The `diagnose()` method is a stub that throws a "Not implemented" error. It must **not** perform directory or configuration analysis.

## Future Services Road Map

This service locator structure will act as the unified registry for downstream Generation 6 platform services:

- **Sprint G6-11**: `LauncherService` implementation (Launch orchestration, execution boundaries).
- **Sprint G6-12**: `DiagnosticsService` implementation (Structure validation, system dependency check).
- **Sprint G6-13**: `InstallerService` (Project workspace layout generation).
- **Sprint G6-14**: `MarketplaceService` (Official catalog updates and dependency management).
