# Project Discovery Specification

## Purpose

Project Discovery is the official platform component of AIOS designed to dynamically recognize and validate projects registered in the Platform ledger (`projects/registry.json`). 

It acts as the single gateway for future runtime services to discover officially recognized workloads, ensuring that all projects are valid, unique, properly structured, and map exactly to the file system.

---

## Discovery Constitution

The Project Discovery module conforms to the following non-negotiable architectural principles of the Generation 6 Platform:

> ### Discovery Never Executes
> 
> 1. **Read-Only Operation**: Discovery is strictly a read-only operation.
> 2. **No Execution/Initialization**: Discovery must never execute, modify, or initialize any project code or assets.
> 3. **Metadata Only**: Discovery produces metadata results only. Runtimes must not be spawned or loaded during this phase.

---

## Discovery Flow

The discovery process is orchestrated in a linear, decoupled pipeline:

```
AIOS Platform
      │
      ▼
[ProjectDiscovery (Orchestrator)]
      │
      ├──> [RegistryReader] ────> Reads & parses raw JSON (No validation)
      │
      └──> [RegistryValidator] ──> Validates schema, ID rules, directories & orphans
      │
      ▼
[ProjectDiscoveryResult] ────────> Emits Success, Project list, Warnings, and Errors
```

---

## Registry Schema Validation Rules

Every project in the registry is validated using the following criteria:

1. **JSON Schema Integrity**:
   - The file `projects/registry.json` must be a valid JSON object.
   - The `version` field must be present.
   - The `projects` field must be a valid array.

2. **Project ID Format (kebab-case)**:
   - Each project ID must consist solely of lowercase alphanumeric characters and hyphens, matching the pattern `/^[a-z0-9]+(-[a-z0-9]+)*$/`.

3. **Project ID Uniqueness**:
   - No two projects in the registry may share the same ID.

4. **Lifecycle Status Validation**:
   - The `status` field must be one of `development`, `production`, or `archived`.

5. **Physical Directory Correspondence**:
   - Each project directory listed in the registry must correspond to an actual, physical subdirectory under `projects/`.

6. **Bijective Mapping (Orphan Detection)**:
   - Every entry in `projects/registry.json` must correspond to exactly one directory under `projects/`.
   - Every physical subdirectory under `projects/` (excluding hidden directories like `.git` and the registry file itself) must be explicitly registered inside `projects/registry.json`. Any unregistered folder triggers an `ORPHAN_PROJECT_DIRECTORY` validation error.

---

## Error Handling

If validation fails, `ProjectDiscovery` returns a failed `ProjectDiscoveryResult` structure containing validation error codes:

| Error Code | Level | Description |
|---|---|---|
| `DISCOVERY_FAILED` | Fatal | Underlying file access or general exception occurred. |
| `INVALID_REGISTRY` | Fatal | File is not a valid JSON object. |
| `MISSING_VERSION` | Error | The registry is missing the specification `version`. |
| `MISSING_PROJECTS` | Error | The `projects` array is missing or malformed. |
| `INVALID_PROJECT_ID` | Error | An entry is missing its project `id` property. |
| `INVALID_PROJECT_NAME` | Error | A project is missing its name. |
| `INVALID_PROJECT_STATUS` | Error | A project has an invalid lifecycle status. |
| `INVALID_ID_FORMAT` | Error | A project ID is not written in `kebab-case`. |
| `DUPLICATE_PROJECT_ID` | Error | Multiple entries use the same project ID. |
| `MISSING_PROJECT_DIRECTORY` | Error | A registered project folder does not physically exist. |
| `ORPHAN_PROJECT_DIRECTORY` | Error | An unregistered directory was found inside `projects/`. |

## Future Extensions

The discovery metadata generated by this module will be utilized in subsequent sprints:

1. **Project Launcher**: Runtimes will invoke `ProjectDiscovery.discover()` to enumerate bootable directories and configure active sandboxes.
2. **Marketplace Integration**: The marketplace manager will query the registry discovery results to filter official core workspaces from third-party community templates.
3. **Plugin & Skill Discovery**: Scanners will only inspect code paths and assets located inside valid discovered project paths.
4. **Knowledge Engine**: Crawlers and vectorization indices will target discovered project scopes to catalog domain context without crawling system folders or orphan directories.
