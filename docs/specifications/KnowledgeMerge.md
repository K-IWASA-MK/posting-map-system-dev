# 知識統合仕様書 (Knowledge Merge Specification)

## 目的
AIOS（品質保証オペレーティングシステム）において、ナレッジベース内に散らばる「重複・類似・断片化されたナレッジ」を静的・動的解析によって特定し、ナレッジベース全体の肥大化および推薦時の競合を防ぐための「統合候補（Merge Candidates）」を生成する仕様を定義する。

---

## 責務
- 同一または類似の意味を持つナレッジの検出。
- 統合候補データモデル（Merge Candidates）の生成。
- **自動マージ実行の絶対禁止**: 本仕様では、マージ計画の「評価・提示」のみを行い、ファイルを自動で書き換えたりマージを実行したりすることは行わない。

---

## 統合判定の対象 (Merge Criteria)
最適化エンジンは、以下の判定基準に基づいてナレッジ同士を統合候補としてマークする。

### 1. 重複ナレッジ (Duplicate Knowledge)
- **判定基準**: 
  - ルール定義の目的や、推奨する適用コードの AST（抽象構文木）または正規表現パターンが90%以上一致している場合。
- **対応方針**: 一方の古いナレッジを廃止（Deprecated）し、最新側にマージ統合することを推奨。

### 2. 類似ナレッジ (Similar Knowledge)
- **判定基準**:
  - 実装方法（例: CSSの微発光の影指定と、別のHTML内での影指定など）はわずかに異なるが、ターゲットとなるルールIDや意味カテゴリが完全に一致する場合。
- **対応方針**: 共通の抽象化ルールとして定義を1つに集約することを推奨。

### 3. バージョン不整合 (Version Difference)
- **判定基準**:
  - 同一内容のナレッジに対して、バージョン（例: `v1.1` と `v1.2`）の定義ファイルが並存して存在し、参照が分散している場合。
- **対応方針**: 最新バージョンへの一本化を推奨。

### 4. 断片化ナレッジ (Fragment Knowledge)
- **判定基準**:
  - 単一ファイル内の極めて局所的な1行の修正ルールなど、独立したナレッジとして管理するメリットが薄い極小の定義。
- **対応方針**: 関連する親ナレッジまたはコンポーネント定義の一部として統合することを推奨。

---

## 統合候補のデータモデル (Merge Candidate Model)
生成される統合候補オブジェクトの定義。

```json
{
  "candidateId": "MC-2026-0005",
  "mergeType": "Duplicate",
  "sourceKnowledgeIds": ["KNW-015", "KNW-018"],
  "destinationKnowledgeId": "KNW-018",
  "similarityScore": 0.96,
  "analysis": {
    "reason": "ボトムナビのLiquid Glassに関するCSS記述がKNW-015とKNW-018で完全に一致しています。",
    "riskOfMerge": "Low"
  }
}
```
