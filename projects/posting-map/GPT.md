# POSTING MAP Philosophy (最優先設計思想)

## このプロジェクトの目的

POSTING MAPは、参政党のボランティアによるポスティング活動を
「誰でも、いつでも、参加しやすくする」ためのプラットフォームである。

目的はシステムを作ることではない。

目的は、
ボランティア活動のハードルを下げ、
地域活動を活性化し、
日本を良くしたいという思いを行動につなげることである。

---

## 最優先原則

POSTING MAPを一般的な在庫管理システム、
配送管理システム、
業務管理システムとして考えてはならない。

必ずPOSTING MAP独自の思想を優先すること。

---

## 解決したい課題

全国には289の小選挙区支部が存在する。

支部には支部長、役員、党員、サポーターが所属している。

ポスティングはボランティア活動であり、
参加者には仕事・家庭・学校などそれぞれ都合がある。

「○日に全員集合してポスティング」

という運用では参加できない人が多く、
活動が広がらない。

POSTING MAPはこの課題を解決するために誕生した。

---

## POSTING MAPの使命

POSTING MAPは、

「チラシを預かっている人」と
「配りたい人」

をデジタルでつなぐプラットフォームである。

地域でチラシを預かっている党員・サポーターを可視化し、
いつでも好きな時間にポスティングへ参加できる環境を提供する。

活動を管理するためではなく、
活動を広げるためのシステムである。

---

## 開発時の絶対ルール

設計に迷った場合は必ず次の問いを最優先にする。

「この機能はボランティアが参加しやすくなるか？」

YESなら採用。

NOなら採用しない。

技術的な美しさより、
現場の使いやすさを最優先とする。

---

## AIへの指示

AIは一般的な業務システムの知識でPOSTING MAPを解釈してはならない。

一般論よりも、
POSTING MAP独自の運用思想を最優先すること。

推測で仕様を補完してはならない。

判断に迷った場合は、
必ずPOSTING MAPの思想へ立ち返ること。

---

## POSTING MAPと北勢CHの役割

POSTING MAPと北勢CHは目的が異なるが、共通して「地域を良くする」という理念を持つ。

### POSTING MAP

対象：
- 参政党の党員
- サポーター

目的：
ボランティアによるポスティング活動を支援し、
誰でも、いつでも参加しやすい環境を提供する。

---

### 北勢CH

対象：
三重第3区を中心とした地域住民。

目的：
地域に役立つ情報を、中立で分かりやすく届ける地域メディアとなること。

北勢CHは政党の宣伝を目的としない。

地域に価値ある情報を継続的に発信し、
信頼される地域メディアとなることを目指す。

その結果として、

「この活動に共感する」
「もっと知りたい」
「一緒に活動したい」

と思う人がいれば、
その人が自ら党員・サポーターになることは歓迎する。

ただし、

北勢CHは無理な勧誘や宣伝を行うメディアではない。

地域への貢献を第一とし、
その信頼の積み重ねを最も大切にする。

---

## 地域メディアの理念

地域メディアの目的は、地域に役立つ情報を継続的に届け、信頼される存在になることである。

地域への貢献を第一とし、無理な宣伝や勧誘は行わない。

地域での活動や理念に共感した人が、自ら地域活動や政党活動に参加したいと考えた場合、その参加を歓迎する。

北勢CHは、この地域メディア運営の実証モデルである。

将来的には、この運営ノウハウとAIOSの共通プラットフォームを活用し、他の地域でもそれぞれの地域メディアを立ち上げ、地域に貢献する活動を支援できることを目指す。

# Product Structure

POSTING MAP は2つのユーザーインターフェースで構成される。

- App
- Dashboard

## App

現場利用を目的としたユーザーインターフェース。

## Dashboard

管理・分析・設定を目的としたユーザーインターフェース。

PCを基本利用環境とするが、スマートフォンではレスポンシブによる簡易表示を提供する。

---

# POSTING MAP Platform Architecture v1 (User Layer)

## 最下層（ユーザーインターフェース構造）

### ① アプリ（App）
- **目的**: 現場作業用（データ収集・現場入力）
- **対象ユーザー**: 配布員 / ボランティア
- **主要機能**: 現場入力、GPS取得、写真撮影・送信、LINEログイン（LIFF）
- **利用デバイス**: スマホ中心（タブレット対応）

### ② ダッシュボード（Dashboard）
- **目的**: 運営・分析・管理用
- **対象ユーザー**: 支部長 / 候補者 / 県連 / 本部 / 運営者
- **利用デバイス**: PCが基本（スマホではレスポンシブによる簡易表示を提供）

### 最重要設計ポイント
**ダッシュボードは別アプリではなく、単一のダッシュボードが画面サイズ（レスポンシブ）に応じて表示を切り替える設計とする。**

---

# POSTING MAP Product Architecture

## 基本原則

POSTING MAP は **単一の App** と **単一の Dashboard** で構成される。

- App は現場でのデータ入力専用である。
- Dashboard は閲覧・管理・分析専用である。
- Dashboard は全組織で共通のシステムを利用する。
- 組織階層によって **集計対象・名称・権限のみが変化**する。
- Dashboard の UI・機能・コードベースは共通とする。

---

# App の役割

App は現場のボランティアが利用する入力ツールである。

主な機能

- LINEログイン
- 配布実績入力
- GPS取得
- 写真撮影・送信
- 配布データ送信

App の役割はデータ取得のみであり、管理機能は持たない。

---

# Dashboard の役割

Dashboard は組織運営・管理・分析を行うためのシステムである。

ボランティアが App から送信したデータを組織単位で集計し、表示する。

Dashboard は一つのシステムであり、ログインした組織によって表示内容が切り替わる。

---

# 組織階層

```
ボランティア
      │
      ▼
    App
      │
      ▼
支部 Dashboard
      │
      ▼
県連 Dashboard
      │
      ▼
ブロック Dashboard
      │
      ▼
本部 Dashboard
```

---

# 組織ごとの集計範囲

| 組織 | 集計対象 |
|------|----------|
| 支部 | 支部所属ボランティアのデータ |
| 県連 | 配下の全支部 |
| ブロック | 配下の全県連 |
| 本部 | 配下の全ブロック |

---

# Dashboard の共通仕様

全階層で共通

- Dashboard
- UI
- 機能
- コード
- データモデル

組織によって変化

- Dashboard 名称
- 集計対象
- 表示データ
- 権限

---

# 開発ルール

Dashboard は複数作らない。

実装する Dashboard は一つだけとし、

- 組織
- 権限
- 集計範囲

によって表示内容を切り替える。

---

# 将来の開発ルール (Future Rule)

今後追加されるすべての Dashboard 機能（AI分析、KPI、地図、レポート、配布予測、エリア分析等）は、単一 Dashboard に追加しなければならない。

組織別に機能を分岐・複製してはならない。

---

# 設計思想

POSTING MAP は **入力システム** と **集計システム** を明確に分離する。

- App = 現場入力
- Dashboard = 組織運営

App は現場の入口であり、製品の中心は Dashboard である。
